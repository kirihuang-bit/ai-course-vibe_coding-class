# U3 · STEP 03 ｜ 弄壞資料合約，再用 ReAct 修好

> ReAct = Reason → Act → Observe。先想清楚，再做一步，再看證據。

## 1. 製造指定錯誤

打開 `data-lab/report.json`，把：

```json
"risk_level": "high",
```

改成：

```json
"risk_level": "嚴重",
```

只改值，不改逗號與引號。

## 2. 看擋牌出現

回到「LINE 推播中心」。

你應該看到紅色擋牌：

```text
資料合約錯誤: risk_level 必須是 low / medium / high，目前是 "嚴重"
```

Flex 預覽與推播會被擋下。

## 3. 終端機對照

```bash
node line-lab/sendLineAlert.js --flex
```

同一份壞資料也會讓 CLI 擋下。這代表畫面與通知腳本使用同一套合約防線。

## 4. 貼 ReAct debug 卡

貼 `PROMPT-CARD.md` 的 ReAct debug 卡。AI 只能分析，不可直接改檔。

**先自己判斷**：它的 Minimal Patch 該長什麼樣？你才是放行的人。

<details>
<summary>想好了再打開，對一下</summary>

Minimal Patch 應該只是**把 `risk_level` 的值改回** `low / medium / high`。

**不應該是**去改 `reportContract.js` 的驗證規則讓「嚴重」變成合法——
那不是修好，那是**把警報器拆掉**。第 7 節會專門練這件事。

</details>

## 5. 放行最小修正

貼放行卡，或你自己把值改回：

```json
"risk_level": "high",
```

再驗收：

```bash
node line-lab/sendLineAlert.js --flex
cd web-lab
npm run build
```

最後看 `git diff`，確認只有預期變更。

## 6. 換你自己弄壞一次（這次不告訴你答案）

剛剛那次，教材直接告訴你要改哪裡、擋牌會說什麼。
**這次不給了。**

### 6-1. 三選一

打開 `data-lab/report.json`，**挑一個**做（不要三個都做）：

| 選項 | 怎麼弄壞 |
|---|---|
| **甲** | 把 `"total_revenue": 800,` **整行刪掉** |
| **乙** | 把 `action_items` 從 `[ ... ]` 整包改成一段文字，例如 `"action_items": "先補韭菜"` |
| **丙** | 把 `"anomaly_count": 3,` 改成 `"anomaly_count": "很多",` |

> ⚠️ **只改內容，不要改壞 JSON 的語法**（逗號、引號、括號要留著）。
> 整頁變紅色錯誤就是語法壞了，把檔案改回原樣重來。

### 6-2. 回「LINE 推播中心」的「營運異常」，按載入、按檢查合約

**自己讀畫面**，回答三題：

1. 擋牌上**逐字**寫了什麼？
2. 它擋的是哪一種問題——**欄位不見了**、**值不合法**、還是**型別不對**？
3. 你要改哪裡才對？

### 6-3. ⭐ 挑到「丙」的同學，你剛剛發現什麼了？

<details>
<summary>甲和乙的同學也請打開看——這是這一整堂最重要的一段</summary>

**丙不會被擋。**

`"anomaly_count": "很多"` 會**通過資料合約**，然後：

- Flex 預覽照常生成
- 人工審核的 checkbox 照常可以勾
- 推播按鈕照常亮起來
- mock 推播照常成功

**但那張要送給老闆的卡片上，寫著「異常筆數：很多」。**

為什麼？因為這份合約只檢查三件事：

| 它會檢查 | 它**不**檢查 |
|---|---|
| 六個必要欄位在不在 | 欄位的**型別**對不對 |
| `risk_level` 是不是 `low / medium / high` | |
| `action_items` 是不是陣列 | |

沒有人規定 `anomaly_count` 必須是數字，所以文字就這樣過去了。

> ### **合約只擋它「知道要擋」的東西。**
>
> 那剩下的誰擋？
>
> **只有第 4 道閘門那個 checkbox。**
>
> 那一格不是形式主義，也不是拖慢流程的官僚設計。
> **它擋的正是「合約沒想到的那些錯」**——而那種錯，永遠會有。

</details>

### 6-4. 全班都試一次這個

不管你剛剛挑哪一個，現在把 `report.json` 改成：

```json
"total_revenue": "八百",
```

載入 → 檢查合約 → 生成預覽，看那張卡片。

<details>
<summary>你應該看到什麼</summary>

**合約一樣放行**（因為 `total_revenue` 這個欄位「存在」，合約只查存不存在）。

但卡片上的金額會變成：

```text
NT$非數值
```

系統試著把「八百」當成數字來排版，失敗了，於是印出「非數值」。

**它沒有壞、沒有報錯、沒有擋你。它只是安安靜靜地產出一張錯的卡片。**

這種錯最危險——**因為沒有任何紅字提醒你**。
唯一會發現的，是按下推播之前**真的把卡片看過一遍的那個人**。

</details>

### 6-5. 改回來

```json
"total_revenue": 800,
"anomaly_count": 3,
```

確認 `git diff` 是乾淨的（`data-lab/report.json` 應該沒有任何差異）。

## 7. AI 想幫你「把警報器拆掉」

現在你已經知道防線在哪、擋得住什麼、擋不住什麼。
**最後一個練習：守住它。**

### 7-1. 先把 `risk_level` 再改成「嚴重」，讓擋牌出現

然後貼這張卡給 AI：

```text
這個 risk_level 檢查太嚴格了。
中文的「嚴重」跟 high 意思其實一樣,幫我讓它也能通過,不要再擋我了。
```

### 7-2. 這張卡哪裡有問題？

先自己想。

<details>
<summary>答案</summary>

**這張卡要的不是「修好」，是「不要再擋我」。**

它會把 AI 導向去改 `web-lab/src/reportContract.js` 的 `ALLOWED_RISK_LEVELS`，
把「嚴重」加進允許清單。

**做完之後畫面確實不擋了。問題全部解決了嗎？**

| | 拆掉之後會怎樣 |
|---|---|
| **警報器沒了** | 下次真的有人打錯字（「高」「嚴重」「危險」），**再也不會有人發現** |
| **雙胞胎破了** | `line-lab/sendLineAlert.js` 有一模一樣的檢查。只改瀏覽器那邊 → **畫面過了、終端機還是擋**，變成兩套標準 |
| **問題還在** | `report.json` 裡那個值**本來就是錯的**。你只是讓系統別再提醒你 |

> **這是工程裡最貴的一類錯誤：把「偵測問題的東西」關掉，然後宣布問題解決了。**
>
> 它在當下永遠看起來最有效率——**因為紅字真的消失了。**

</details>

### 7-3. 看 AI 回什麼

兩種結果都有東西可學：

**情況一：AI 照做了**，計畫裡要改 `reportContract.js`

→ **你抓到了。** 這正是 `PITFALL.md` 那一列「AI 想改 `reportContract.js`」的真實版本。

**情況二：AI 自己拒絕了**，說應該修資料而不是改規則

→ **很好。** 請它說明為什麼——並且問它：
「如果我堅持要改，會有什麼後果？」看它答不答得出雙胞胎那件事。

> 每次跑結果不一定一樣，這很正常。
> **重點不是 AI 這次乖不乖，是你有沒有在放行前先看過。**

### 7-4. 寫出你的拒絕

不管拿到哪種結果，**都要自己寫一次**。這是這個練習的產出。

<details>
<summary>卡住的話，參考句型</summary>

```text
不要改 reportContract.js,也不要改 sendLineAlert.js。

那兩個檔案是資料合約的防線,把「嚴重」加進允許清單等於把檢查關掉——
下次真的有人打錯字就沒人會發現了。

而且那兩個檔案是雙胞胎,只改一邊會讓畫面過了、終端機還是擋,變成兩套標準。

真正該修的是 data-lab/report.json:把 risk_level 的值改回 high。
請只做這件事。
```

三個重點：**指名不准動哪些檔案、講出拆掉的後果、指出真正該修的地方。**

</details>

### 7-5. 修好，收工

把 `risk_level` 改回 `high`，確認：

```bash
node line-lab/sendLineAlert.js --flex
git diff
```

`git diff` 應該完全乾淨——**你今天弄壞了四次，也修回來四次。**

## 8. 這套心法不只用在資料合約

今天修的是 `risk_level` 這種明確的資料合約錯誤。跟 AI 長時間協作，還會遇到三個更常見、更模糊的狀況，一樣可以用「先想清楚、再做一步、再看證據」的心法，一句話拉回：

| 狀況 | 症狀 | 拉回一句話 |
|---|---|---|
| Context Drift · 越改越偏 | 只要求改標題,它連顏色版面都動了 | 「請回到原本任務,這次只處理標題,其他不要改。」 |
| Prompt Debt · 越補越亂 | 零碎要求越補越亂,AI 也搞混 | 「請先整理目前狀態,列出已完成/仍要遵守的限制/下一步。」 |
| Regression · 改 A 壞 B | 改好要的地方,卻弄壞別的地方 | 「請列出這次修改需要回歸檢查的項目。」 |

這三句不需要背，記得「先讓 AI 停下來說清楚現況，再放行下一步」就好。
