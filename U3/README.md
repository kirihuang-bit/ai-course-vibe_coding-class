# U3 ｜ 訂單看板、LINE Flex、人工審核：控制 AI 能不能「動手做事」

> **U2 管的是 AI 能寫什麼 code。U3 管的是 AI 能不能對真實世界採取行動。**

寫錯的 code 可以改回來。**送出去的 LINE 訊息收不回來。**

所以這堂會出現一整排**閘門**：資料要先檢查過、卡片要先預覽過、人要先勾過，
按鈕才會亮。這不是介面設計得囉嗦，是這堂課的主題本身。

> **今天你幾乎不會寫程式。** 你要做的是**看、判斷、放行**。
> 如果你覺得「今天怎麼沒在寫東西」——那正是這堂課要練的：
> **在真實工作裡，決定「可以送出去了」的人，通常不是寫 code 的那個人。**

## 這堂的骨架：五道閘門

「LINE 推播中心」有五顆按鈕，**必須照順序按，前一顆沒過，後一顆就是暗的**：

| # | 按鈕 | 這道閘門在擋什麼 |
|---|---|---|
| 1 | 載入資料 | 沒有資料就沒有東西可送 |
| 2 | **檢查資料合約** | 欄位缺漏、`risk_level` 不合法 → **擋下，不讓你往下走** |
| 3 | 生成 Flex 預覽 | 你要**親眼看過卡片長什麼樣**，才知道自己要送什麼出去 |
| 4 | **☑ 我已人工審核** | **這一格只有人能勾。** 系統算得再對也不會自己勾 |
| 5 | 推播 LINE Flex | 前面四關都過，才送得出去 |

> **為什麼要五道，不能一鍵送出？**
>
> 因為每一道擋的是不同的錯：
> 第 2 道擋**資料錯**，第 3 道擋**內容錯**，第 4 道擋**判斷錯**。
>
> 第 4 道最特別——**它擋的是「沒有人負責」**。
> 系統算出「庫存不足」是一回事，「決定現在要通知老闆」是另一回事。
> 後面那件事永遠要有一個人簽名。
>
> 這就是 **human-in-the-loop**（人在迴圈裡）：
> 自動化可以做完 99%，但**送出去的那一下必須有人按**。

## 三種訊息，走同一條路

| 類型 | 顏色 | 資料哪裡來 |
|---|---|---|
| 訂單資訊 | 藍 | 看板的即時訂單（沒開店就退回 `data-lab/orders.json`） |
| 庫存警示 | 琥珀 | 伺服端依**現在的庫存**即時算出來 |
| 營運異常 | 紅 | `data-lab/report.json` |

三種都走 `載入 → 檢查合約 → 預覽 → 人工審核 → mock 推播`。
**流程一樣，只有資料來源不同**——這是真實系統的常態。

## 今天不會真的送 LINE

主線的正確結果是看到這一行：

```text
[mock] LINE_REAL_SEND is not 1, no request sent.
```

> **看到 `[mock]` 就是過關，不是手機收到才算過關。**
>
> `mock` 是「假送」：流程完整跑一遍，但最後不真的送出去。
> 有 LINE OA 的同學可以做進階真送，**沒有完全不影響過關**。

## 今天會碰的檔案

**你只需要改一個檔案，而且是為了「把它弄壞」：**

```text
data-lab/report.json      ← STEP-03 故意改壞 risk_level，再修回來
line-lab/.env             ← 進階真送才需要（沒有 LINE OA 就不用碰）
```

**這三個檔案 AI 想改就擋下來：**

```text
web-lab/src/reportContract.js    ← 資料合約的防線
line-lab/sendLineAlert.js        ← 同一套防線的另一半
web-lab/orderSim.js              ← 訂單模擬引擎
```

> **為什麼特別點名這三個？** 因為 STEP-03 你會製造一個錯誤，
> 而 AI 最常見的「修法」是**去改檢查規則，讓錯誤變成合法**。
>
> 那不是修好，那是**把警報器拆掉**。
> 前兩個檔案是刻意寫成一模一樣的「雙胞胎」——畫面和終端機各一份，
> 你等一下會親眼看到同一份壞資料被擋兩次。

## C3 要學會的技術力

- **輪詢（polling）**：看板每 3 秒問一次後端，資料才會「活」起來
- **API / payload**：說得出前端打哪個網址、送什麼結構的資料
- **token 邊界**：說得出 token 為什麼只能在後端，並且**用 DevTools 證明給自己看**
- **mock vs real**：分得出「流程跑完」和「真的送出去」
- **webhook 的方向**：知道它是外面打進來，跟推播相反
- **資料合約**：說得出 `risk_level` 只能是 `low / medium / high`，以及為什麼要有這種規定
- **human-in-the-loop**：說得出那個 checkbox 為什麼不能由系統自己勾
- **ReAct**：先想清楚 → 做一步 → 看證據，而不是叫 AI「幫我修好」
- **最小修正**：修的是壞掉的資料，不是放寬檢查規則
- **知道防線的極限**：說得出**有哪一種錯合約擋不住**，以及那時候誰才擋得住
- **守得住防線**：AI 提議「把檢查放寬一點」時，說得出拆掉它會有什麼後果

## 名詞速查表

> **不用背。** 這張表是給你**中途卡住、想不起來某個字是什麼意思時回來查的**。

| 名詞 | 在這門課的意思 | 你要能說出什麼 |
|---|---|---|
| **輪詢 polling** | 前端每隔幾秒主動問後端「有新資料嗎」 | 看板每 3 秒打一次 `/api/orders` |
| **API** | 前後端講好的呼叫入口 | 就是那些 `/api/...` 開頭的網址 |
| **payload** | 送出去的那包結構化資料 | Flex Message 是 JSON，不是一段文字 |
| **JSON** | 一種資料寫法，大括號加欄位 | 人和程式都讀得懂 |
| **token** | 呼叫外部平台的鑰匙 | 只能在 `.env`，不進前端、不進 Git（U0 講過） |
| **env var** | 不寫進程式碼的環境設定 | `LINE_REAL_SEND` 決定假送還真送 |
| **mock** | 假送：流程跑完但不真的送出去 | 看到 `[mock]` 就是主線過關 |
| **webhook** | 外面主動打進來的事件通知 | 方向跟推播**相反** |
| **Flex Message** | LINE 上有顏色、分區塊的卡片訊息 | 不是純文字 |
| **資料合約** | 大家講好「這份資料必須長什麼樣」 | 少欄位或值不合法就會被擋下 |
| **`risk_level`** | 風險等級欄位 | 只能是 `low` / `medium` / `high` |
| **擋牌** | 資料不合約時畫面上的紅色警告 | 它出現是**防線有效**，不是壞掉 |
| **雙胞胎防線** | 畫面和終端機用同一套檢查規則 | 同一份壞資料會被擋兩次 |
| **human-in-the-loop** | 自動化流程裡刻意留給人的那一步 | 那個 checkbox 只有人能勾 |
| **DevTools / Network** | F12 打開，看瀏覽器實際發出哪些請求 | 用它證明 token 沒有外洩 |
| **component** | 畫面的一塊積木 | `OrderBoard.jsx` 裡的 `OrderLane` |
| **安全量** | 低於這個數字就該補貨 | 韭菜是 5、醬料包是 200，**每種料不一樣** |
| **ReAct** | 先想 → 做一步 → 看證據 | 不是直接叫 AI「幫我修好」 |
| **Minimal Patch** | 能解決問題的最小改動 | 改壞掉的資料，不是改檢查規則 |
| **CLI** | 在終端機下指令 | `node line-lab/sendLineAlert.js --flex` |
