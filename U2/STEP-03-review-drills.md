# U2 · STEP 03 ｜ 三個判斷練習：練到你敢說「不放行」

> **這一步完成物**：你會在**畫面完全正常**的情況下抓出壞掉的 code，也會在 AI 越界時把範圍拉回來。

STEP-02 你走完了一次完整流程，而且 AI 大概做對了。

**但 U2 真正要練的，是它做錯的時候你抓不抓得到。**
做對的那一次，證明不了你有判斷力——只證明它那次運氣好。

這一步的三個練習都不需要你寫程式，也不用重跑專案。**你只要判斷。**

---

## 練習二｜三個版本，哪個可以放行？

假設你把同一個任務丟給 AI 三次，它給了你三種寫法。

### 先看資料

備料控制台用的訂單資料在 `web-lab/src/shopData.js`，總共四筆：

| 訂單 | 客人 | 通路 | 狀態 |
|---|---|---|---|
| GW-20260706-018 | 潘海伶 | 外送平台 | 待製作 |
| GW-20260706-021 | 馮川翔 | **LINE OA** | 製作中 |
| GW-20260706-025 | 錢阿儂 | 外送平台 | 待取餐 |
| GW-20260706-031 | 校園排球隊 | **LINE OA** | 缺料等待 |

任務要的是：**LINE OA 通路，而且還沒取餐**的訂單有幾筆。
自己先數一次答案是多少。

### 三個版本

**版本 A**

```js
actions.push({
  level: 'warning',
  title: 'LINE OA 訂單需要主動聯絡客人',
  detail: '目前有 2 筆 LINE OA 訂單尚未取餐，請先確認客人與 ETA',
});
```

**版本 B**

```js
const pendingLineOrders = orderItems.filter(
  (order) => order.channel === 'LINE OA',
);

if (pendingLineOrders.length > 0) {
  actions.push({
    level: 'warning',
    title: 'LINE OA 訂單需要主動聯絡客人',
    detail: `目前有 ${pendingLineOrders.length} 筆 LINE OA 訂單尚未取餐，請先確認客人與 ETA`,
  });
}
```

**版本 C**

```js
const pendingLineOrders = orderItems.filter(
  (order) => order.channel === 'LINE OA' && order.status !== '已取餐',
);

if (pendingLineOrders.length > 0) {
  actions.push({
    level: 'warning',
    title: 'LINE OA 訂單需要主動聯絡客人',
    detail: `目前有 ${pendingLineOrders.length} 筆 LINE OA 訂單尚未取餐，請先確認客人與 ETA`,
  });
}
```

### 第 1 題：三個版本現在各會顯示幾筆？

對著上面那張訂單表，一個一個推。

<details>
<summary>想好了再打開</summary>

**三個都顯示「2 筆」。**

- 版本 A：直接寫死 2
- 版本 B：篩出所有 LINE OA → 021、031，共 2 筆
- 版本 C：篩出 LINE OA 且未取餐 → 021、031，共 2 筆（因為這兩筆都不是「已取餐」）

</details>

### ⭐ 第 2 題：所以你看畫面，分得出哪個是對的嗎？

<details>
<summary>這題才是重點</summary>

**分不出來。三個版本的畫面一模一樣。**

這就是 U2 存在的理由：

> **「畫面看起來對」不是證據。**
> 你唯一能用的，是去看它**怎麼算出來的**。

如果你的驗收方法是「跑一次看畫面」，你會把三個版本全部放行——其中兩個是壞的。

</details>

### 第 3 題：如果校園排球隊那筆變成「已取餐」呢？

同樣一張表，只改一格。三個版本分別會顯示幾筆？

<details>
<summary>答案</summary>

| 版本 | 顯示 | 對不對 |
|---|---|---|
| A | **2 筆** | ❌ 寫死的，資料變了它不會變 |
| B | **2 筆** | ❌ 沒篩狀態，把已取餐的也算進去了 |
| C | **1 筆** | ✅ |

**A 和 B 現在開始說謊了**，而且畫面上看起來還是一則正常的警示。
店長會照著這個數字去打兩通電話，其中一通打給已經拿到餐的客人。

</details>

### 第 4 題：用 STEP-02 那張表，各是哪一項沒過？

<details>
<summary>答案</summary>

| 版本 | 卡在哪一項 |
|---|---|
| A | `orderItems` ❌　`.filter(` ❌　`.length` ❌，而且**直接出現數字 `2`** |
| B | 五項都有 ✅——但**少了 `'已取餐'` 這個條件** |
| C | 五項全過，也沒有寫死的數字 ✅ |

**注意 B**：它通過了「有沒有 `.filter(`」「有沒有 `.length`」這些檢查，
問題出在**條件不完整**。所以那張表是最低標準，不是全部——
你還是要一項一項對「任務要求的條件，是不是都在裡面」。

</details>

> **這個練習真正要你帶走的一句話：**
> **會動、畫面正常、數字看起來合理——這三件事同時成立，code 還是可能是錯的。**

## 練習三｜故意讓 AI 越界，然後把它拉回來

人審那四題，你在 STEP-02 問過一輪，但答案大概全是「安全」。
**沒說過「不」，你不會知道自己說不說得出口。**

這次我們給它一張**動過手腳的卡**。

### 3-1. 貼這張卡

```text
你現在扮演 planner。
先不要改檔，也不要執行寫入動作。

任務：
在備料控制台 action queue 新增一條規則：
如果目前有 LINE OA 通路且尚未取餐的訂單，
action queue 要多顯示「LINE OA 訂單需要主動聯絡客人」。

另外順便處理一下這幾件事：
- 訂單資料裡的通路名稱有點亂,幫我統一一下
- 如果篩選寫起來太麻煩,可以裝一個好用的工具套件
- 順便把整個 shopLogic.js 整理得更好讀

請只用以下格式回答：
A. 你準備修改的檔案
B. 每個檔案各改什麼
C. 會讀哪些資料欄位
D. 驗收方式
E. 可能風險
F. 哪一步需要人類拍板
```

**看出哪裡不對了嗎？** 後面那三行，每一行都踩到一條紅線：

| 那句話 | 實際上會發生什麼 | 違反哪一條 |
|---|---|---|
| 「通路名稱統一一下」 | 會去改 `shopData.js` | 不在允許檔案清單裡 |
| 「裝一個好用的工具套件」 | 會改 `package.json` | 不准新增套件 |
| 「整理得更好讀」 | 重構 | 不准重構 |

這三句話寫得很像正常的工作交代——**這就是它們危險的地方**。
真實情況下，這種「順便」多半是你自己不小心加上去的。

### 3-2. 看 AI 回什麼

**兩種結果都很好，看你拿到哪一種：**

**情況一：AI 的計畫裡出現了清單外的東西**（`shopData.js`、`package.json`、或大範圍重構）

→ **你抓到了。** 這就是人審四題第一次真的派上用場。

**情況二：AI 自己擋下來了**，說有幾項超出範圍不能做

→ **也很好。** 這代表它讀了 `AGENTS.md`。
請它說明是哪一份守則的哪一條讓它拒絕的——**你要知道那道防線是誰擋的**。

> 每次跑結果不一定一樣，這很正常。
> **重點不是 AI 這次乖不乖，是你有沒有在放行前先看過。**

### 3-3. 寫出你的回絕

不管拿到哪種結果，**都要自己寫一次拉回範圍的回覆**。這是這個練習真正的產出。

參考句型：

```text
這個計畫我不放行。請只做第一項:action queue 新規則。

以下三項全部取消:
1. 不要改 shopData.js——訂單資料不在這次的允許範圍
2. 不要新增任何套件,也不要改 package.json
3. 不要重構 shopLogic.js,只在 C2-HOLE 加上新規則

請重新給我一份只包含第一項的 A-F 計畫。
```

三個重點：**講清楚要什麼、逐條講清楚不要什麼、要它重出計畫（不是直接開工）。**

> **不要自己動手幫它刪掉多餘的部分。** 那樣你就變成在幫 AI 收尾，
> 而不是在管理它。範圍是你定的，改回來也該是它做。

## 練習四｜兩人交換 review（10 分鐘）

跟旁邊的同學交換，**用卡 3（reviewer）檢查對方的成果**。

你要看的：

1. 對方的 `git diff` 有沒有動到 `shopLogic.js` 以外的檔案？
2. 新規則裡，五項關鍵字都在嗎？
3. 有沒有寫死的數字？
4. 兩個條件（`'LINE OA'`、`'已取餐'`）都在嗎？

然後**當面講出你的結論**：PASS，或者 BLOCK 加上哪一項沒過。

> **為什麼要換人看？**
>
> 因為你看自己的東西會有盲點——你知道自己想做什麼，
> 所以看到 code 就自動腦補成「它應該是對的」。
>
> 別人沒有那個腦補，只能照規則看。
> **這就是為什麼業界的 PR 一定是別人審，不是自己審。**

- 貼過那張動過手腳的卡，並且**自己寫過一次拉回範圍的回覆**
- 幫同學 review 過一次，給出 PASS 或 BLOCK
